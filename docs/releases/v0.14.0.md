# Desk v0.14.0 — draft

This release is not yet qualified or published. Complete the release-wide notes
and validation evidence before publication; this draft records the approved
storage scope: the storage line is off.

## Storage

**Storage in v0.14.0 behaves as in v0.13.2.** Chats, drafts, attachments,
retained runs and backups are kept where v0.13.2 keeps them, in the same files,
and a v0.13.2 installation opens unchanged. Desk does not measure or account
for its storage, sets no limits, never starts read only for a storage reason,
and refuses no work for storage. Several Desks may run on one installation,
any project may be started with the same settings and data folders, and
project moves, Desk home moves, chat data moves and backups work as in
v0.13.2. Admin → Storage & backups shows pack files, chat data and Policy
recovery, without storage accounting; the status strip has no storage notice.
Child-component growth is neither measured nor capped, as before.

The storage line described below is built into this release but switched off
([ADR-0015](../adr/0015-storage-line-off-in-v0.14.0.md)). Turning it on
(`JPACK_DESK_STORAGE_LINE=on`) is for development and its CI lane only, and is
not supported for use. An installation that a development build with the line
on already set up still opens with it off, and its chats read and save; Desk
home moves stay refused there.

## Off in this release; arrives in v0.15.0

The storage line covers limits and admission for Desk-owned storage, including
concurrent reservations, retention and safe recovery under storage pressure
([Desk #685](https://github.com/Judgment-Pack/judgment-pack-desk/issues/685),
[Desk #698](https://github.com/Judgment-Pack/judgment-pack-desk/issues/698)).
None of the following applies to v0.14.0:

- **Measurement and limits.** Desk measures its storage at first use; Admin →
  Storage shows the usage, the limits and whether a scope is over budget, and
  a "Storage needs attention" notice warns. Limits were to be advisory at
  first, with accurate counting and enforcement later; growth that would leave
  less than the free-space headroom on a measured filesystem is refused.
- **What storage measures, and the read-only start.** Every file and folder
  under the registered folders that belongs to the person running Desk is
  measured. Content storage cannot account for (another user's, a link, a
  special file, anything a group or other users can write) starts Desk read
  only until fixed. Folders Desk makes that are not registered yet, desks
  added to a Desk home and named desks are measured and listed as warnings.
- **One Desk at a time.** One Desk per installation; a second Desk with the
  same settings and data folders exits at startup.
- **The first project's seal.** Without a Desk home, storage belongs to the
  project Desk was first started on, and another project started with the
  same folders exits at startup. A project given an identity later keeps its
  storage, with a warning.
- **A project moved outside Desk.** Desk does not start on a project folder
  moved or renamed outside Desk, and asks for Move to….
- **Finishing a move's settings conflict.** A settings file edited between a
  move's rename and its finish starts Desk read only, with Finish the move with
  the moved settings under Admin → General → Desk home.
- **Desk home moves after storage is set up** are refused in words until home
  moves carry storage with them.
- **Child roots.** Child-component roots are measured and low space is warned
  about; enforcement follows with the bounded-storage contracts of Runtime
  v0.40.0, Gateway v0.25.0 and Runner v0.28.0
  ([Desk #693](https://github.com/Judgment-Pack/judgment-pack-desk/issues/693)),
  currently planned for Desk v0.18.0.

## Native approval continuation limits

This candidate adopts Agent v0.13.2. In its native subscription path, an approved
call can execute and retain its result without that result reaching the model
([Agent #309](https://github.com/Judgment-Pack/judgment-pack-agent/issues/309)).
Desk displays the retained result's original text directly in the response,
including after reload and after a later approval replaces the current one.
Non-text result content is identified separately; this is not a raw JSON export.
Do not rely on the model's subsequent answer as evidence that it saw the result.
This limitation is accepted for Desk v0.14.0; its fix is planned for Agent
v0.14.0.

Native continuation of a Plan decision after an answered action approval is
refused as `NativePlanAfterApprovalUnsupported` before further dispatch. A native
released Plan pause with delegated children enabled is refused as
`NativePlanDelegationUnsupported`
([Agent #317](https://github.com/Judgment-Pack/judgment-pack-agent/issues/317)).
The prior Plan, approval result and journals remain retained. Ordinary native
chat remains available. Desk does not enable package task-step scheduling;
restored scheduling state is refused by the published context boundary before
model or effect dispatch. These are compatibility limits, with no live-model
answer-quality claim.

## Exact-text approval on the native path

Desk shows an approval from the exact text that runs and binds the decision to
that text's digest; the shown text and the digest move together
([Desk #694](https://github.com/Judgment-Pack/judgment-pack-desk/issues/694)).
The API path is validated for exact large integers, trailing decimal zeros,
nested objects and out-of-range numbers. The native subscription path stays
limited: on Agent v0.13.2 an approval asked for a custom-source action can be
recorded as a cancellation, leaving the run's head running with the approval
asked instead of paused
([Agent #342](https://github.com/Judgment-Pack/judgment-pack-agent/issues/342)).
Desk does not treat that head as a decidable pause, does not author a paused
checkpoint, and runs nothing; the request text is kept exactly. This was seen in
a Desk harness with the actual native bridge, and its reach in production is
inferred from source. This limitation applies to Desk v0.14.0 only and ends
when Agent v0.14.0 is published.

## Approved results refused by the record guard

On Agent v0.13.2, an approved action can run before its durable result is refused
because the record guard redacts text in that result, such as a local home or
temp path ([Agent #343](https://github.com/Judgment-Pack/judgment-pack-agent/issues/343)).
After the execution owner stops, Desk shows that the approved action may have
run, its result was not kept, and its outcome is unknown. Desk does not replay
that action or offer a retry that runs the same original request again. Read or
reload the retained response to inspect this warning; do not treat an incomplete
canonical checkpoint as success or run the action again.

The guard remains enabled, actual results are not replaced or allow-listed, and
Desk does not author a replacement checkpoint. This maintainer-approved
limitation applies to Desk v0.14.0 only and ends when Agent v0.14.0 is published. Agent v0.13.2 remains pinned for this candidate. This result-storage
limitation is separate from the native model-delivery limitation in Agent #309.

## Critiques not compared with saved cases

On Agent v0.13.2 the critic cannot compare a proposal with the project's saved
cases ([Agent #344](https://github.com/Judgment-Pack/judgment-pack-agent/issues/344)).
Rehearsing a saved case is a Runtime act call, and the critic reading admits no
act call, so each rehearsal is refused before it reaches the Runtime. A critique
therefore says that the saved cases were not compared and that it cannot say the
proposal was not refuted. That is a missing comparison, not the proposal failing.
Desk passes the Runtime's tool taxonomy through as published: it does not
relabel the call, admit act calls during the critic reading, or rehearse outside
the Agent's gate. This maintainer-approved limitation applies to Desk v0.14.0
only and ends when Agent v0.14.0 is published.

## Answers to retained questions

An explicit answer in saved chat starts a new durable run under the same admitted
chat context and original request and scope. Desk retains the parent run,
question and exact answer as linked user history. The parent's completed
checkpoint, operation receipts and canonical journal stay read-only. Repeated
delivery of the same answer action returns the saved successor link; it never
starts that run again. A refused admission or preparation leaves the question
pending. Reload follows saved links without dispatching work.

The successor receives its own default allowance. Prior Used, Limit and Grants
are not cumulative across these runs. If more compute is needed, the successor
pauses for an explicit person-decided grant. Answers grant no tool approval or
effect authority, and completed or uncertain operations are not replayed. This
change preserves the existing saved-chat answer scope; it does not add standalone
authoring continuations or native parking.

This follows Agent v0.13.2, where a question's answer is a new run and no
supported way carries an earlier run's allowance into it
([Agent #340](https://github.com/Judgment-Pack/judgment-pack-agent/issues/340)).
Carrying that allowance is planned for Agent v0.14.0; until Desk adopts it, this
limitation stands.

This draft records candidate behavior. Actual API/native producer checks,
browser readers, independent review and release-wide validation remain required
before qualification; no live-provider or answer-quality result is claimed here.
