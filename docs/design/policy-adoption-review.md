# Desk private Policy adoption API (first slice)

Official independently published Policy draft `policy-v1.0.0-draft.1`, format 1.0.0, pinned Spec `0799b37b74e35c4a86bfbf70f7bee80bdb7bbe94` ([normative draft](https://github.com/Judgment-Pack/judgment-pack-spec/blob/0799b37b74e35c4a86bfbf70f7bee80bdb7bbe94/spec/policy.md)). Desk-private review state; this offline draft check grants no execution, approval, IAM or live source authority. Existing manual admission remains a separate exact-profile, explicitly authorized workflow.

- `GET /api/policy-adoptions/options?pack=<configured-alias>` → bounded exact saved-byte Pack publications and compatible current approved coverage choices.
- `GET /api/policy-adoptions` → `{items: AdoptionSummary[]}` bounded 256, current authenticated administrator. Summary: id, revision, candidateDigest, pack (existing exact coverage Pack selector), dependencies (exact selections), reviewState, updatedAt.
- `POST /api/policy-adoptions` accepts exactly one of:
  - `{action:"prepare",operationId,pack:{publicationId,artifactId,version,content:{sha256,bytes}},coverages:[{policyId,coverageId,revision,candidateId,reviewId}]}`. Nonempty max 16. Server resolves whole-narrative scope + current approved coverage head and complete Policy/lifecycle/source/ownership/recovery basis; duplicates and mixed consumers refused. Runtime official draft canonical/check runs outside metadata write lock. New immutable candidate + unique portable adoption identity each time; separate explicit review always required.
  - `{action:"review",operationId,adoptionId,baseRevision,candidateDigest,basisDigest,decision:"approve"|"request-changes",comment?}`. Exact current immutable candidate, complete basis CAS and fresh Runtime check on approve. No editable/subset dependency array in review.
- `GET /api/policy-adoptions/{adoption}` → AdoptionReply.
- `GET /api/policy-adoptions/{adoption}/history` → same bounded reply with retained immutable review history.
- `GET /api/policy-operations/{operation}` → existing read-only recovery; no replay.

AdoptionReply: `{revision,document:{schemaVersion:1,id,createdAt,updatedAt,candidate:{id,digest,content,portableId,formatVersion:"1.0.0",basisDigest,pack,dependencies,document,materials,check},reviewState:"unreviewed"|"reviewed"|"changes-requested",currentReviewId?,reviews:[{id,sequence,candidateId,candidateDigest,basisDigest,decision,comment?,at,actor,check?}]},readiness:{status:"ready"|"stale"|"unavailable",reason?},eligibility:{status:"effective"|"not-yet-effective"|"ineligible"|"unavailable",reason?},recovery?,recoveryBoundary?:{snapshotId,restoredAt,sequence}}`. Candidate `content` references private retained envelope; `document` references canonical portable adoption; materials include complete retained closure. Dependencies expose exact selection + pinned policyRevision/lifecycleRevision/sourceRevision and policyPublicationId, scope, statement. Runtime report lives in retained `check` reference. Responses retain immutable candidate/history even if current readiness or eligibility changes.

Mutation response uses existing `{delivery:"committed"|"recovered",outcomeKind:"adoption",policyId,policyRevision,adoption:AdoptionReply,receipt}`. policyId is first chosen dependency's private Policy ID solely for existing operation anchoring; policyRevision is complete basisDigest. Receipt has adoptionId, adoptionRevision, adoptionCandidateId, candidateDigest, reviewId when reviewed. This anchoring never restricts the complete chosen set.

Runtime unavailable/unsupported → preparation refuses with explicit runtime-unavailable/unsupported-contract, no mutation. Existing saved history stays readable. Readiness describes whether retained basis is still current. Eligibility describes live lifecycle separately, and never grants execution. Published/scheduled dependencies may be reviewed; withdrawn/expired/superseded, old-owner publications, historical restored publications, unavailable authority cannot be approved. Restored adoption reviews remain historical and inactive; fresh destination candidate/review required.

All errors use existing `{code,message,outcome:"not-committed"|"unknown",currentRevision?}`; operation IDs are persisted before the browser dispatch, uncertain outcomes recover by GET, never automatic replay.

## Implemented storage and verification

Private ledger schema 2 has an optional bounded `adoptions` map. A record contains one immutable candidate content reference and at most 512 explicit reviews. Candidate identity is `adoption_candidate_<random>`; portable identity is `urn:desk:adoption-candidate:<candidateId>` with independent artifact version 1.0.0. Preparing a changed set always creates a new record and identity. Portable Policy documents use a separate candidate identity derived from the exact private Policy publication, never the prototype Policy identity.

The immutable envelope retains the exact Pack publication witness, full chosen dependency order, coverage content and approved review snapshots, Policy/lifecycle/source/authority revisions, original publication source, whole-narrative scope, and statement. A dependency may carry `coverageRecovery` (snapshotId,restoredAt,sequence) to prove its exact historical coverage revision. Replies may carry `recoveryBoundary` with the same bounded marker alongside `recovery`; this permits offline reconstruction of historical operation revisions after multiple restores. These fields are private metadata and convey no portable authority.

The configurable existing Runtime Policy subprocess boundary verifies both contracts. Prototype calls keep their existing flags and checks. Official draft calls explicitly use `--format-version 1.0.0`, exact pinned profile/provenance/capabilities, `draft` maturity, complete `candidateResult`, bounded output, valid process exit, canonical-byte digests, exact document meaning/identity and refusal semantics. The API field names `candidateCapabilities` and `candidateResult` remain for compatibility. Full-document conformance, approval verification, execution authority, live authority and network acquisition flags remain explicitly false. Successful checks cover exact supplied bytes, section anchors and scoped Core references; they do not establish semantic Policy correctness or current source/admission authority. No local schema compiler or Core number normalization was added. The generated candidate Policy says workspace-managed; source content, original, review basis and Pack are retained unchanged. Portable adoption bytes are canonicalized and checked by Runtime.

The chosen set limit is 16 Policies, subject to Runtime's stricter aggregate caps: at most 16 material registrations, 262144 bytes per companion document, 1048576 bytes per ordinary material, 4194304 bytes per original, 16777216 distinct retained bytes and 24 MiB material carrier. The same bytes under different media roles still consume distinct registrations. Therefore fewer than 16 Policies may fit. Oversized sets return unsupported-contract before any adoption metadata/operation receipt is committed. Private candidate envelopes are bounded to 2 MiB, records to 256, and operation history uses the existing 4096 limit. Options are bounded to 256 Pack choices and 256 coverage rows and signal truncation.

Preparation and approval resolve approved current coverage heads against the exact Pack publication, refuse duplicate Policies and awaiting interpretation, validate historical coverage evidence, and require current Desk ownership with a publication beyond ownership/recovery boundaries. Published and scheduled releases may be prepared/reviewed while eligibility says not-yet-effective. Withdrawn, expired, superseded, restored inactive publications and unresolved source updates are ineligible. Runtime runs outside the metadata write lock; current authentication, selected coverage/source/ownership/recovery/lifecycle bases, lifecycle time and Pack publication bytes are rechecked within the transaction before commit. Request changes can be retained without Runtime or available Pack publication storage.

Archive closure verifies canonical candidate contents and complete raw material roles offline, plus exact historical coverage prefixes and review reports. Every operation reply is bound to a provable immutable candidate and reconstructed metadata/review prefix. Restore retains history and installs an inactive adoption boundary; previous reviews cannot be approved at the destination. A new eligible destination candidate and separate explicit review are required. Archived pre-publication candidate reports remain valid only under their exact historical Spec `0852c5fa7726e51b36e574a5b110e7f5e012e03d` contract, maturity, capabilities and result semantics. Archive verification accepts that frozen contract without rewriting document or report bytes. Fresh preparation and approval require the official draft Runtime contract; an old or mismatched Runtime returns actionable unavailability while saved drafts and history remain available. Prototype 0.0.2 coverage and its fresh checks remain unchanged and explicitly legacy. Promotion of the draft metadata does not migrate documents, approvals, Jobs, registrations or grants. Existing manual admission retains its independent exact release/runtime, lifecycle, ownership, signer and explicit-action gates; the offline report cannot grant authority.

Focused Go checks cover complete-set review, exact substitutions and duplicate/omitted selections, current coverage/source basis, withdrawal/expiry/publication races, current authentication including recovery, precommit and uncertain writes without replay, untrusted/missing archive material and malformed historical receipts, inactive restore, exact saved-byte options, closed HTTP fields/query and no-store, candidate Runtime response faults, raw Core numbers and aggregate registration bounds. Real Runtime fixtures use `JPACK_POLICY_TEST_BIN`; CI supplies the actual pinned published Runtime and requires explicit PASS lines for official draft exact-byte checks, archive role resolution and legacy prototype coverage, so an absent fixture cannot silently skip that gate. Earlier first-slice implementation used explicitly selected gpt-6.1-sol/xhigh; official draft adoption used explicitly selected gpt-6.1-sol/high. No document-byte conversion or automatic replay occurs.
