# Project memory

Implemented in Desk, 2026-10-14. This complements bounded per-execution context and the optional `jpack-assistant.json` project brief.

## Controls and ownership

Admin → Assistant → Project memory has independent **Use saved memory** and **Suggest memories** switches, both initially off. Turning either off retains the stored entries. Add, edit, review, forget and clear operate in the same project. Inferred suggestions remain pending until the person chooses Remember; an exact explicit `remember: …`, `remember this: …`, `remember that …` or `/remember …` command can save directly. The AI cannot approve its own inferred entry. A source-chat link and updated date remain visible. Chat also exposes durable canonical proposal review. Explicit person remember commands remain separate and never accept a canonical model proposal.

Desk stores preferences and corrections in an owner-only `ai-memory-<history identity hash>.json` in the active conversation storage directory (normally the Desk's `.desk-private/data`). It is not a repository instruction file and is not committed or shared automatically. Project moves retain the original history namespace. Storage relocation and backups include it. Deleting one topic forgets its superseded versions as well. Hashed tombstones block reconstruction from the same old message; Clear also sets a timestamp cutoff. An explicit new remember command can restore a topic, while old sources stay blocked.

## Context and reliability

Every API dispatch and Codex request uses the canonical server context preparation functions. Relevant approved entries are selected locally from the latest user request, bounded to five entries and the released Agent memory byte budget (currently 4,000 bytes). The model can also call `recall_memory`. Recall is keyword based, without a vector database or a second paid model call. This means paraphrases without shared terms may not retrieve a memory. Current instructions and saved artifacts always take precedence; memory is never evidence or approval.

Suggestion provenance is bound by the host to the latest saved user turn, checked again on the server. Independent critics and child tasks cannot write memories. The canonical candidate permits root authors to propose through reserved `remember {kind,text}` in Plan; this does not store memory or leave Plan. Children, critics and reformatting runs cannot propose. Only the separate authenticated person review stores a canonical proposal. Only explicit management actions and the verified direct command create active memories. Common credential patterns are refused; this is not an exhaustive secret detector.

File-dependent entries carry digests; changed sources mark them stale and exclude them from recall. Existing tools currently suggest stable textual preferences, not automatic artifact summaries. There is no background transcript crawling or automatic import of CLAUDE.md, AGENTS.md, old context files, or other providers' memory stores. Stale entries can be forgotten and replaced with a current reviewed memory. Clear removes memory text; chats and user project files remain intact.

The store uses bounded strict JSON, owner permissions, symlink checks, atomic replacement/readback, shared storage locks and revision checks for management writes. It holds at most 256 entries. There is no silent overwrite or provider-specific bypass. New AI features inherit the shared recall boundary and must pass its architecture tests.

## Released Agent record projection

Agent v0.9.1 receives closed typed Memory records from the canonical server host. Desk extends its existing private version-1 memory schema with optional canonical metadata and retains its existing controls. Only active, unexpired, relevant entries whose file dependencies still match are eligible; Use saved memory must be enabled. Ranking remains keyword relevance followed by update time. Selection counts the released reader’s canonical serialized record bytes, skips entries that do not fit, and retains at most five.

Each manually accepted entry becomes an accepted project-scoped reference with `text` equal to its key, a colon and space, and its exact stored text. Its text digest uses the released SHA-256 helper. Its record identity and `source.run` are opaque host import identities bound to the project history namespace and every retained entry field, including version timestamps, original source and dependencies. The projection uses `proposedBy: host`; it does not claim that an old saved chat or turn was an Agent run. Identical stored versions keep the same identity; edited versions and other projects get different identities. The stored creation timestamp is preserved exactly, and a malformed timestamp refuses context preparation instead of inventing history.

An optional entry `canonical` object retains `id`, `kind`, `source` (`run` and `proposedBy`), `digest` and optional `expiresAt`. Enriched entries preserve exact proposed text, identity, kind, source and digest; their canonical text has no management topic prefix. Creation time stays in the existing `createdAt` field, and scope remains project. The released Memory reader validates every enriched record and its content digest, including expired and pending entries; malformed, unknown, null or duplicate canonical identities refuse private reads and backup imports. Legacy documents remain valid without a migration or a GET write. Management edits remove canonical metadata before saving the changed version, giving it a new host identity; approving an unchanged pending entry preserves its canonical identity. No management request can supply canonical metadata.

The metadata-only `MemoryLifecycle` callback compares retained accepted identities with all current eligible records independently of relevance and the recall count/byte bounds. Forgotten, cleared, superseded, edited, disabled or dependency-invalid versions become revoked. An otherwise eligible version whose expiry has passed becomes expired. Prior terminal states remain terminal. The execution prompt host freezes one private store/dependency snapshot for lifecycle and recall, including shared callbacks from delegated children; Agent owns the immutable recalled records for the rest of that run. A resumed execution constructs a fresh prompt host. Concurrent management changes take effect at the next run or resume boundary. Prior metadata never reconstructs deleted text or creates an identity. An eligible entry omitted by query relevance alone receives no terminal update. Agent's existing request, phase and admission checks still apply before resume; changing the retained request requires a new response.

Canonical metadata stays outside entry text and legacy recall JSON; it is available to private management and backup readers. The bounded [canonical proposal acceptance](canonical-memory-acceptance.md) extension adds separate authenticated person review in this same store. Neither slice adds a replacement remember tool, permission/evidence authority or global factory activation. Explicit person remember commands and reviewed management keep their existing behavior. See [Canonical memory lifecycle](canonical-memory-lifecycle.md) for the tested boundary and remaining work.


## Canonical proposal controls and review

In the canonical execution candidate, Suggest is captured in the immutable saved-chat source binding. Suggest-off supplies the released nested project policy `budget.memoryProposalsPerRun: 0`; Suggest-on inherits the released table. A later Suggest change causes the existing current-source check to refuse active or resumed execution, requiring a new response rather than changing its admitted budget. Use remains independent and continues to drive recall/lifecycle. Turning Suggest off does not prevent a person from reviewing an already retained proposal. Independent creation review actions (`establish-cases`, `propose-correction`) capture proposal authority as false even when Suggest is on; they receive canonical cap zero and cannot supply acceptance attribution. Non-chat purposes cannot accept without the required saved human turn.

GET projects pending canonical checkpoint proposals into the existing memory list without copying them into the memory entries or writing a migration. Accept, decline and edit require the exact retained run revision, proposal ID/digest, current authenticated session/person/project/chat, latest bound saved user turn and memory-store If-Match. The host derives a stable canonical-kind/content topic key and any dependency from a retained verified saved-pack read; the model supplies neither management IDs nor paths. Source changes, tombstones, Clear's user-turn cutoff, sensitive text, expiry and existing limits refuse acceptance. Decline completes only the reviewed proposal; it never stores its text.

Unchanged acceptance retains canonical ID/digest/source/creation/expiry. Edited acceptance creates a distinct person identity and digest while retaining kind and expiry; an exact receipt links the reviewed proposal. The entry and metadata-only receipt commit in one atomic memory-document replacement. Receipts are bounded to 512 and retained after Forget/Clear so a completed delivery can be reconciled without recreating content. Receipts and review metadata are outside recalled text. Unknown replies never trigger automatic mutation retries; GET/reload/Stop only observe. See [Canonical proposal acceptance](canonical-memory-acceptance.md).
